## What I built

### `src/cli.ts`

The only new file under `src/`. It exports `run(argv, io)` and, when run directly, calls it and sets
`process.exitCode`. Commands:

- `draw <file> [-o <dir>]`: loads the file, lays it out, checks the drawing, writes `<dir>/<name>.svg`
  and `<dir>/<name>.png`, and prints one line. `<dir>` defaults to `out`, the folder is created if
  missing, and `<name>` is the file name without `.schem.json` or `.json`.
- `--help`, `-h`, `help` and no arguments: the usage text, with
  `npm run schem -- draw examples/led.schem.json` as the example.
- `--version`: the version from `package.json`.

Exit codes are `0` for drawn and valid, `1` for drawn but not valid, and `2` when nothing was drawn.
The valid test is the same as `scripts/draw.ts`: the layout status is `valid` and `checkDrawing`
passes both layers 1 and 2. Invalid drawings still write both files, then print the verifier errors
and overlaps on their own lines.

The file is read once, then `JSON.parse` decides whether it is valid JSON. When it is not, a small
scanner in `cli.ts` finds the offset of the syntax error and turns it into a line and column and a
plain sentence. This is needed because Node's own message gives a position for only some errors. Load
errors are printed one per line from `loadProject` (the function `readProject` uses). An unknown part
type also prints `Known part types and their pins are listed in docs/parts.md.`

A user mistake never prints a stack trace. Only an unexpected exception in the engine goes through
`Internal error, please report it:` and then the stack. Write failures for the output folder are
reported as `Cannot write to <dir>: <message>`.

### `package.json`

Added `"schem": "tsx src/cli.ts"` and `"docs:parts": "tsx scripts/parts-doc.ts"`. No dependencies and

### `examples/`

Five files in the official form, made by loading the validation case with `readProject` and writing
it with `saveProject` (a throwaway script outside the repo, since deleted):

| File | From | Title in the file |
|---|---|---|
| `led.schem.json` | `case01-led.json` | LED with a current-limiting resistor |
| `summing-amp.schem.json` | `case03-summing.json` | Inverting summing amplifier |
| `h-bridge.schem.json` | `case04-hbridge.json` | H-bridge motor driver |
| `i2c-sensors.schem.json` | `case05-i2c.json` | ESP32 with two I2C sensors |
| `esp32-relay.schem.json` | `case06-esp32-relay.json` | ESP32 relay driver |

All five load with no errors and no warnings, draw valid, and return `0`.

Fields removed, in every file where they were present:

- `meta.nextNetId` and `meta.nextHintId` (editor counters, not needed to draw).
- `circuit.nc` when it was an empty list.
- `intent` when every value was the default (empty hints and locks, empty overrides, `clean`/`ieee`
  style).
- `assets` when `definitions` was empty.

`esp32-relay.schem.json` keeps `assets` because it embeds the `module:esp32-devkitc-v4` definition.

For `h-bridge` and `esp32-relay` I first removed `ext` too, because my throwaway script removed it
unconditionally. That was wrong: their `ext` holds the phase0 case provenance, which is not a default.
I restored both `ext` blocks. The final files keep that provenance. This goes slightly beyond the
brief's candidate list of "empty ext", so it is also listed under open questions.

Each file's SVG was compared before and after trimming: the text was identical for all five. After
restoring `ext` in the two files, their SVG still matched the trimmed version, which is expected
because `ext` is inert.

`examples/README.md` has one line per example and the draw command.

### `scripts/parts-doc.ts` and `docs/parts.md`

`npm run docs:parts` writes `docs/parts.md` from `BUILTIN` and `MODULE_LIBRARY`, sorted by type. The
first line is exactly:

```
Generated by npm run docs:parts. Do not edit by hand.
```

The table has one row per library part type (26 rows: 22 symbols and 4 modules) with the module name
for modules, the pin numbers in backticks, each pin's name, its aliases, and the pin groups. The
introduction explains the three endpoint forms: `R1[1]` by number, `D1.anode` by name or alias, and
`U1{GND}` by group. `ic` and `header` have no library pins, so they are a short paragraph rather than
rows; see the open questions.

### `docs/netlist-format.md`

A guide to writing a file by hand: the top-level fields, a part, a net, the three endpoint forms,
power and ground names, `circuit.nc`, and a note that `intent` exists and is described in `SPEC.md`.
`examples/led.schem.json` is quoted in full; I checked the quoted block against the file and it is
byte-identical.

Every section ends with a `checked:` comment naming the file and function I checked. I limited those
checks to `src/io/project.ts`, `src/core/model.ts` and `src/core/validate.ts`. The document leaves out
`assets`, `layout`, `ext`, a net's `domain`, and the older short endpoint form (`B1.+`), because the
brief asked for the three main fields plus `intent`, and for the official form. Those are open
questions below.

### `tests/cli.test.ts`

Calls `run` directly with temporary files and folders. It checks:

- all five examples return `0` and write a non-empty SVG and PNG with the right signatures;
- `--help`, `-h` and no arguments print usage, and `--version` prints the `package.json` version;
- a missing file returns `2` and names the file;
- a JSON syntax error on line 5 returns `2` and the message names line 5 and a column;
- an unknown part type returns `2`, names the type and mentions `docs/parts.md`;
- a pin that does not exist returns `2` and names the endpoint;
- bad arguments return `2`;
- none of these outputs contains `    at ` (a stack trace).

The bad inputs are written in the test's own temporary folder.
